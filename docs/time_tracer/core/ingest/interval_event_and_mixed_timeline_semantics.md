# Interval Event And Mixed Timeline Semantics

本文定义 TimeTracer 当前的“区间事件（interval event）”与“点事件 +
区间事件混用”业务语义。

本文是该能力的业务口径。实现、验证规则或其他文档与本文冲突时，
应显式核对当前 contract 和回归测试，不要依赖历史实现倒推语义。

## 1. 目的

引入区间事件后，系统需要同时支持两类作者态记录方式：

1. 连续打点式记录
2. 只记录某些明确时间段的选择性记录

本文回答以下问题：

1. 什么是点事件，什么是区间事件
2. 两类事件混用时如何确定活动起止时间
3. 未记录时间是否允许为空白
4. 哪些情况是合法缺口，哪些情况应视为非法重叠或倒序
5. 查询、统计、报表如何解释“未记录时间”

本文同时定义“只有结束时间的活动事实（end-only）”。它不是 TXT 中新增的
作者态标记，而是点事件在缺少可靠开始边界时的解析结果。

## 2. 术语

### 2.1 点事件（point event）

作者只记录一个时间点和一个活动 token 的事件行。

示例：

```text
1353睡觉
```

语义：

1. `1353` 表示该活动在 `13:53` 结束，或在该时刻发生一次活动切换
2. 该事件本身不自带显式开始时间
3. 它的开始时间需要由上下文时间边界推导

### 2.2 区间事件（interval event）

作者明确记录开始时间、结束时间和活动 token 的事件行。

示例：

```text
0900-1030概率统计
```

语义：

1. `0900` 是显式开始时间
2. `1030` 是显式结束时间
3. 该事件本身已经构成一个完整活动区间

### 2.3 只有结束时间的活动事实（end-only）

end-only 是点事件在当前连续时间线上没有可靠开始边界时的解析结果。

例如：

```text
d0101
090000学习
```

如果当天及其可用前置上下文都没有更早的可靠结束边界，则该活动保留：

1. `start = null`
2. `end = 09:00:00`
3. `duration = null`

它仍然是有效活动事实，计入活动次数和活动明细，但不计入活动时长。

end-only 的结束时间仍然是可靠时间边界。下一条点事件可以使用它作为开始时间；
如果后续重新导入后获得了更早的可靠边界，则该记录可以重新解析为完整区间。

在 Core 领域模型中，活动事实的 `kind` 与边界形状必须一致：

1. `kInterval` 必须同时有非空的开始和结束时间。
2. `kEndOnly` 必须只有非空结束时间，开始时间为空；派生时间戳和时长由转换阶段保持为
   无开始边界、零时长。
3. 新建活动事实应使用领域模型提供的 interval/end-only 构造入口；结构校验会拒绝
   `kind` 与时间边界不一致的记录。

### 2.4 最后已知时间边界（last known boundary）

混用模式下，系统在单日时间线上维护一个“当前最后已知边界”。

它表示：

1. 到目前为止，作者已经明确给出的最近一个可靠结束时间
2. 后续点事件若需要推导开始时间，应优先从这个边界起算

### 2.5 未记录时间（unrecorded gap）

作者没有记录任何事件的时间段。

示例：

```text
0900-1030概率统计
1401-1900睡觉
```

其中 `1030-1401` 就是未记录时间。

## 3. 两类事件行

当前口径下，单日内部允许出现两类事件行：

1. 点事件：`HHMM + activity token`
2. 区间事件：`HHMM-HHMM + activity token`

两类事件都允许带行内备注，唯一备注分隔符是 `//`。备注可在后续物理行
继续书写，续行也以 `//` 开头。

示例：

```text
1353睡觉 // nap
0900-1030概率统计 // chapter 3
```

## 4. 统一时间线规则

### 4.1 当前原则

无论作者使用点事件还是区间事件，最终都应转换为标准活动事实。活动事实可以是：

1. 完整区间：`start_time`、`end_time`、`duration`、`project_path`
2. end-only：只有 `end_time` 和 `project_path`，没有可确定的 `start_time` 与 `duration`

系统应维护一条统一的单日时间线，而不是让两类事件各自采用不同的统计口径。

### 4.2 点事件的区间推导

点事件的结束时间就是它自己的 `HHMM`。

其开始时间由“最后已知时间边界”决定：

1. 若存在最后已知边界，则 `start = last_known_boundary`
2. 若不存在最后已知边界，则按当日已有 wake / continuation 规则决定能否取得首段起点
3. 若仍无法取得可靠起点，则生成 end-only 活动事实，不伪造开始时间和时长

### 4.3 区间事件的区间推导

区间事件自带显式开始和结束时间：

1. `start = explicit_start`
2. `end = explicit_end`

区间事件生成标准 record 后，应把“最后已知时间边界”推进到它的显式结束时间。

### 4.4 混用时的边界推进

无论当前事件是点事件还是区间事件，只要它成功生成了合法活动事实，
系统就应把“最后已知时间边界”推进到该 record 的结束时间。

因此：

1. 点事件之后，边界推进到点事件的 `HHMM`
2. 区间事件之后，边界推进到区间事件的 `end`

end-only 的结束时间同样会推进最后已知时间边界，因此下一条点事件可以从该
结束时间开始计算。

### 4.5 区间事件的归属日期

区间事件必须在开始记录时确定并固定一个 `attribution_date`（归属日期）。
归属日期不是保存操作发生当天，也不能在保存时根据 `TODAY` / `YESTERDAY`
等相对选项重新解析。

当前规则是：

1. `attribution_date` 取区间开始时所选目标的逻辑日
2. 如果产品使用 06:00 的逻辑日切换点，则开始时间在 `00:00-05:59:59`
   的区间归入前一个逻辑日
3. 结束时间可以跨越自然日边界，但不因此改变归属日期
4. 一条跨午夜区间仍是一条完整区间，不自动拆分成两天
5. 用户后续编辑开始/结束时分秒，只修改区间边界，不改变已固定的归属日期

例如：

```text
开始：2026-07-22 23:00:00
结束：2026-07-23 07:00:00
归属：2026-07-22
```

该区间的持续时间是 8 小时，原始 TXT 仍写入 `d0722` 对应的日块。
Android 或其他 presentation 在草稿中必须保存绝对日期（例如 ISO
`2026-07-22`），而不是只保存相对日期枚举。

## 5. 混用示例

示例：

```text
d0101
0606w
0900-1030概率统计
1353睡觉
```

应按如下方式理解：

1. `0606w` 建立 wake 相关日语义
2. `0900-1030概率统计` 是一条显式区间事件
3. 该区间结束后，最后已知时间边界更新为 `10:30`
4. `1353睡觉` 是点事件
5. 它的开始时间应取最后已知时间边界 `10:30`

因此，`1353睡觉` 对应的标准活动区间应为：

```text
10:30 -> 13:53
```

而不是回退去使用更早的 `06:06` 或 `09:00`。

## 6. 选择性记录与空白时间

### 6.1 空白时间允许存在

引入区间事件后，系统必须允许作者只记录自己关心的时间段。

示例：

```text
d0101

0900-1030概率统计
1401-1900睡觉
```

这里的 `1030-1401` 缺口是合法且预期的。

它表示：

1. 用户不想记录这段时间
2. 或用户认为这段时间不值得记录
3. 系统不应替用户猜测这段时间属于什么活动

### 6.2 未记录时间不参与统计

未记录时间：

1. 不自动补成某个“未知活动”
2. 不自动归属给前一个活动
3. 不自动归属给后一个活动
4. 不参与 `Total Time Recorded`

因此，`Total Time Recorded` 的含义仍然是：

```text
sum(all recorded activity durations)
```

而不是：

```text
first recorded start -> last recorded end
```

### 6.3 这属于预期行为，不是数据错误

当作者刻意只记录学习、睡眠或工作等特定活动时：

1. 查询结果存在时间缺口是正常现象
2. 报表总时长小于全天跨度是正常现象
3. 这不属于逻辑校验错误

## 7. 合法与非法边界

### 7.1 合法情况

以下情况应视为合法：

1. 只有点事件
2. 首个点事件因缺少上下文而成为 end-only
3. 只有区间事件
4. 点事件与区间事件混用
5. 中间存在未记录时间缺口
6. 同一天只记录少量明确区间
7. 区间跨越自然日，但归属日期已在开始时固定

### 7.2 非法情况

以下情况应视为非法：

1. 区间事件的结束时间早于开始时间，且不满足合法跨日规则
2. 新区间与最后已知时间边界发生重叠
3. 区间事件显式开始时间早于最后已知时间边界
4. 点事件的结束时间早于最后已知时间边界
5. 任意两条最终标准 record 在同一时间线上形成重叠

### 7.3 缺口不是非法，重叠才是非法

本文明确区分：

1. gap（空白）是允许的
2. overlap（重叠）是不允许的

系统需要保护的是“不能重复计时”，而不是“必须覆盖整天”。

## 8. Day Completeness 的新解释

引入区间事件后，不能再简单用“authored event 数量是否小于 2”判断一天是否
具备基本统计意义。

例如：

```text
0900-1030概率统计
```

虽然只有 1 条 authored event，但它已经是一条完整活动区间。

因此：

1. “事件条数少”不再自动等价于“区间不可计算”
2. day completeness 需要区分“点事件未闭合”与“区间事件已自洽”
3. 作者态 warning 规则需要后续按本文重新定义

## 9. 查询、统计、报表口径

所有查询与报表都应继续基于标准 record facts，而不是基于原始文本行直接统计。

区间事件引入后，口径应保持为：

1. 先把点事件和区间事件转换为完整区间或 end-only 活动事实
2. 活动明细、活动次数和活动树 occurrence count 包含 end-only
3. duration、Total Time Recorded、时长聚合和平均时长只统计完整区间
4. end-only 在 timeline 和 Markdown 中只显示结束时间，不伪造开始时间

因此，活动树、日报、周报、月报、recent、range 都不需要把空白时间视作隐式活动。

## 10. 与现有语义的关系

### 10.1 继续保留的语义

以下语义继续保留：

1. wake anchor / continuation day 规则
2. 跨日、跨月 sleep link 规则
3. alias mapping 只决定 canonical activity path，不决定时间语义
4. 统计口径基于 record facts，而不是文本原词

### 10.2 已淘汰的旧口径

以下旧口径不再是当前语义：

1. “所有活动事实都必须有可计算的 start/end/duration”
2. “系统只记录时间点，不记录显式开始/结束”
3. “`<2 authored events` 就意味着很多区间不可计算”
4. “点事件默认近似覆盖整天”的隐含连续性心智
