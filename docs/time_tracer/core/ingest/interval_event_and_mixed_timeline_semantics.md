# Interval Event And Mixed Timeline Semantics

本文定义 TimeTracer 即将引入的“区间事件（interval event）”与“点事件 +
区间事件混用”业务语义。

它的目标是先固定目标规则，再指导后续实现与旧文档回填。

若当前实现尚未完全覆盖本文规则，应将本文视为目标业务口径，而不是把旧实现
行为反向视为权威。

## 1. 目的

引入区间事件后，系统需要同时支持两类作者态记录方式：

1. 连续打点式记录
2. 只记录某些明确时间段的选择性记录

本文回答以下问题：

1. 什么是点事件，什么是区间事件
2. 两类事件混用时如何确定活动起止时间
3. 未记录时间是否允许为空白
4. 哪些情况是合法缺口，哪些情况应视为非法重叠或倒序
5. 查询、统计、报表如何解释“未记录时间”

## 2. 术语

### 2.1 点事件（point event）

作者只记录一个时间点和一个活动 token 的事件行。

示例：

```text
1353睡觉
```

语义：

1. `1353` 表示该活动在 `13:53` 结束，或在该时刻发生一次活动切换
2. 该事件本身不自带显式开始时间
3. 它的开始时间需要由上下文时间边界推导

### 2.2 区间事件（interval event）

作者明确记录开始时间、结束时间和活动 token 的事件行。

示例：

```text
0900-1030概率统计
```

语义：

1. `0900` 是显式开始时间
2. `1030` 是显式结束时间
3. 该事件本身已经构成一个完整活动区间

### 2.3 最后已知时间边界（last known boundary）

混用模式下，系统在单日时间线上维护一个“当前最后已知边界”。

它表示：

1. 到目前为止，作者已经明确给出的最近一个可靠结束时间
2. 后续点事件若需要推导开始时间，应优先从这个边界起算

### 2.4 未记录时间（unrecorded gap）

作者没有记录任何事件的时间段。

示例：

```text
0900-1030概率统计
1401-1900睡觉
```

其中 `1030-1401` 就是未记录时间。

## 3. 两类事件行

目标口径下，单日内部允许出现两类事件行：

1. 点事件：`HHMM + activity token`
2. 区间事件：`HHMM-HHMM + activity token`

两类事件都允许带行内备注，备注分隔符延续现有规则：

1. `//`
2. `#`
3. `;`

示例：

```text
1353睡觉 // nap
0900-1030概率统计 # chapter 3
```

## 4. 统一时间线规则

### 4.1 目标原则

无论作者使用点事件还是区间事件，最终都应转换为标准活动区间：

1. `start_time`
2. `end_time`
3. `duration`
4. `project_path`

系统应维护一条统一的单日时间线，而不是让两类事件各自采用不同的统计口径。

### 4.2 点事件的区间推导

点事件的结束时间就是它自己的 `HHMM`。

其开始时间由“最后已知时间边界”决定：

1. 若存在最后已知边界，则 `start = last_known_boundary`
2. 若不存在最后已知边界，则按当日已有 wake / continuation 规则决定能否取得首段起点
3. 若仍无法取得可靠起点，则该首段视为“上下文暂缺”

### 4.3 区间事件的区间推导

区间事件自带显式开始和结束时间：

1. `start = explicit_start`
2. `end = explicit_end`

区间事件生成标准 record 后，应把“最后已知时间边界”推进到它的显式结束时间。

### 4.4 混用时的边界推进

无论当前事件是点事件还是区间事件，只要它成功生成了合法标准 record，
系统就应把“最后已知时间边界”推进到该 record 的结束时间。

因此：

1. 点事件之后，边界推进到点事件的 `HHMM`
2. 区间事件之后，边界推进到区间事件的 `end`

## 5. 混用示例

示例：

```text
0101
0606w
0900-1030概率统计
1353睡觉
```

应按如下方式理解：

1. `0606w` 建立 wake 相关日语义
2. `0900-1030概率统计` 是一条显式区间事件
3. 该区间结束后，最后已知时间边界更新为 `10:30`
4. `1353睡觉` 是点事件
5. 它的开始时间应取最后已知时间边界 `10:30`

因此，`1353睡觉` 对应的标准活动区间应为：

```text
10:30 -> 13:53
```

而不是回退去使用更早的 `06:06` 或 `09:00`。

## 6. 选择性记录与空白时间

### 6.1 空白时间允许存在

引入区间事件后，系统必须允许作者只记录自己关心的时间段。

示例：

```text
0101

0900-1030概率统计
1401-1900睡觉
```

这里的 `1030-1401` 缺口是合法且预期的。

它表示：

1. 用户不想记录这段时间
2. 或用户认为这段时间不值得记录
3. 系统不应替用户猜测这段时间属于什么活动

### 6.2 未记录时间不参与统计

未记录时间：

1. 不自动补成某个“未知活动”
2. 不自动归属给前一个活动
3. 不自动归属给后一个活动
4. 不参与 `Total Time Recorded`

因此，`Total Time Recorded` 的含义仍然是：

```text
sum(all recorded activity durations)
```

而不是：

```text
first recorded start -> last recorded end
```

### 6.3 这属于预期行为，不是数据错误

当作者刻意只记录学习、睡眠或工作等特定活动时：

1. 查询结果存在时间缺口是正常现象
2. 报表总时长小于全天跨度是正常现象
3. 这不属于逻辑校验错误

## 7. 合法与非法边界

### 7.1 合法情况

以下情况应视为合法：

1. 只有点事件
2. 只有区间事件
3. 点事件与区间事件混用
4. 中间存在未记录时间缺口
5. 同一天只记录少量明确区间

### 7.2 非法情况

以下情况应视为非法：

1. 区间事件的结束时间早于开始时间，且不满足合法跨日规则
2. 新区间与最后已知时间边界发生重叠
3. 区间事件显式开始时间早于最后已知时间边界
4. 点事件的结束时间早于最后已知时间边界
5. 任意两条最终标准 record 在同一时间线上形成重叠

### 7.3 缺口不是非法，重叠才是非法

本文明确区分：

1. gap（空白）是允许的
2. overlap（重叠）是不允许的

系统需要保护的是“不能重复计时”，而不是“必须覆盖整天”。

## 8. Day Completeness 的新解释

引入区间事件后，不能再简单用“authored event 数量是否小于 2”判断一天是否
具备基本统计意义。

例如：

```text
0900-1030概率统计
```

虽然只有 1 条 authored event，但它已经是一条完整活动区间。

因此：

1. “事件条数少”不再自动等价于“区间不可计算”
2. day completeness 需要区分“点事件未闭合”与“区间事件已自洽”
3. 作者态 warning 规则需要后续按本文重新定义

## 9. 查询、统计、报表口径

所有查询与报表都应继续基于标准 record facts，而不是基于原始文本行直接统计。

区间事件引入后，口径应保持为：

1. 先把点事件和区间事件都转换为标准活动区间
2. 再基于这些标准 record 进行数据库写入
3. 查询、树聚合、报表只统计已记录区间

因此，活动树、日报、周报、月报、recent、range 都不需要把空白时间视作隐式活动。

## 10. 与现有语义的关系

### 10.1 继续保留的语义

以下语义继续保留：

1. wake anchor / continuation day 规则
2. 跨日、跨月 sleep link 规则
3. alias mapping 只决定 canonical activity path，不决定时间语义
4. 统计口径基于 record facts，而不是文本原词

### 10.2 需要升级的语义

以下旧口径需要后续文档与实现同步升级：

1. “事件行只可能是 `HHMM + token`”
2. “系统只记录时间点，不记录显式开始/结束”
3. “`<2 authored events` 就意味着很多区间不可计算”
4. “点事件默认近似覆盖整天”的隐含连续性心智
