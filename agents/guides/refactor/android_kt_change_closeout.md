# Android Kotlin 修改后的收尾工作指南

## 目的

本指南用于 Android Kotlin 功能修改完成后的收尾阶段。目标不是追求更少的行数或更“抽象”的代码，而是在不改变已完成行为的前提下，按童子军原则让本次触及的代码至少不比修改前更难维护。

适用范围包括 `apps/android/**` 中本次功能直接修改的 Kotlin、Compose UI、状态、路由、DataStore 偏好、测试和资源文件。

## 开始前

1. 先阅读 `agents/rules/AGENTS.md` 和 `apps/android/AGENTS.md`。
2. 按 `apps/android/AGENTS.md` 的路由补读对应 Android 文档，尤其是：
   - `docs/time_tracer/presentation/android/specs/EDIT_ROUTING.md`
   - `docs/time_tracer/presentation/android/specs/BUILD_WORKFLOW.md`
   - 触及持久化时的 `docs/time_tracer/presentation/android/specs/preference-storage.md`
3. 明确功能行为已实现，并先完成针对功能的验证。收尾重构不得承担尚未完成的功能需求。
4. 使用 `git diff` 和 `git status` 确定本次改动边界；保留用户已有的无关修改。

## 收尾检查：应该做什么

逐项检查本次新增或修改的代码。只有能明确改善可维护性的项目才实施，并将无行为变化的整理放入独立 `refactor` commit。

### 1. 职责是否清楚

一个类、函数或 Composable 应只承担一个紧密相关的职责。

- 如果 UI 渲染、状态转换、持久化、业务校验混在一起，且这些部分会独立变化，按职责拆分。
- 如果它们共同构成一个连续工作流、共享同一组不变量，则保持在一起以维护高内聚。
- 拆分后的每个单元应有清晰名称和独立变化理由，而不是仅把代码搬到新文件。

### 2. 命名是否准确

变量、函数、类型、回调、DataStore key 和测试名应表达当前领域含义，而不是历史实现细节。

- 名称应说明“是什么”或“发生什么”，而非旧 UI 形态或偶然实现方式。
- 例如 Quick Access 从内联面板改为底部抽屉后，`assistSettingsExpanded` 应改为 `quickAccessEditorVisible`。
- 对于无兼容要求的内部持久化 key，应一起改名，避免代码语义与存储语义不一致。

### 3. 状态与副作用是否分离

纯状态转换应可独立理解和测试；副作用应有清晰边界。

- reducer、状态构造和纯格式化/校验函数不应直接执行文件写入、数据库同步、JNI 调用、导航或弹窗。
- 文件写入、数据库同步、网络/JNI、导航和弹窗等副作用，应集中在协调器、ViewModel、route 或明确的事件处理边界。
- 不在 Composable 渲染路径中隐藏业务写入或跨层调用。

### 4. 依赖方向是否正确

确认新增代码仍遵循模块和领域边界。

- UI 不复刻核心 TXT、校验、查询或业务规则。
- `feature-*` 不直接依赖 JNI；runtime 负责 JNI/bridge 实现。
- bridge/codec 只做协议转换，不承载业务语义。
- core 不依赖 Android 或 Compose。
- 优先通过最小 gateway 接口依赖，而非无差别使用 aggregate runtime gateway。

### 5. 重复是否会漂移

只收敛真正可能导致规则分叉的重复。

- 同一业务规则、错误转换、持久化策略或边界计算被多个路径复制时，应考虑收敛到拥有该语义的位置。
- 仅外观相似、但上下文和变化原因不同的 Compose 代码，不应为了去重强行抽象。
- 抽取后调用点应比原来更清楚；若只是增加跳转，则保留局部实现。

### 6. API 是否表达完整意图

检查参数、布尔值和回调是否容易被误用。

- 多个相互关联参数、多个语义不明的 Boolean、或笼统回调名，是考虑请求对象、状态对象或更精确名称的信号。
- 不为“优雅”而增加层次；只有在减少调用错误、隐藏不变量或使调用意图更明确时才调整 API。
- 默认参数应只用于真实可选的行为；不要为旧调用点保留已经失真的默认语义。

### 7. 保持高内聚

相关流程、规则和不变量应保留在一起。

- 文件行数不是拆分依据。
- 能连续阅读并理解一个完整能力的代码，即使较长，也可以保留在同一文件。
- 只有出现独立复用、独立测试、独立变化或清晰所有权转移时，才按职责拆分。

### 8. 清理本次引入的噪声

删除或修正本次修改留下的无效内容：

- 死代码、无用 import、过时注释；
- 临时日志、临时 TODO、无效 fallback；
- 已经失真的兼容分支或旧命名；
- 本次新增但没有真实用途的默认参数、状态或包装层；
- 与本次功能无关的大面积格式化、行尾变化或文件移动应避免混入。

### 9. 独立提交并验证

重构应能独立审查、独立回滚。

1. 功能 commit：只说明行为、契约、测试数据或用户可见变更。
2. `refactor` commit：只包含无行为变化的职责、命名、局部重复或边界改进。
3. `test`/`docs` commit：如补测或文档调整具有独立意图，可单独提交。
4. 重构后运行与功能相同或更聚焦的回归验证；Android Gradle 命令必须串行执行。

## 明确不应该做什么

- 不按文件行数机械拆分文件。
- 不为了“看起来更抽象”引入通用层、基类、工具类、泛型、配置化或设计模式。
- 不为了消除一次性或上下文不同的相似代码而牺牲可读性。
- 不顺手重写整份文件、统一整模块风格，或扩展到无关调用链。
- 不在 `refactor` commit 中改变功能、业务规则、DataStore/文件格式、公开契约、错误语义或性能特征。
- 不把大面积 import 排序、格式化、行尾变化、资源重排或文件移动混进功能/重构提交。
- 不为了追求“零技术债”阻塞已完成的功能交付。
- 不覆盖、回退或清理工作区中无关的用户修改。

## 发现既有问题时的范围判定

阅读本次触及文件时，可能发现文件其他区域也有明显维护问题。是否一并重构，使用以下判断：

可以纳入本次独立 `refactor` commit，前提是至少满足一项：

- 本次新增代码会经过、依赖或共享该区域的状态/不变量；
- 不修会迫使本次代码复制错误模式或形成明显维护风险；
- 修复能低风险、独立且无行为变化地完成；
- 改动范围能够用一句话说明，并能用现有或聚焦测试验证。

不应纳入本次改动的情况：

- 只是发现该文件整体较旧、较长或风格不统一；
- 与本次功能没有直接交互；
- 需要改变契约、数据格式、业务语义或大范围测试基线；
- 无法在独立 commit 中清楚审查和回滚。

这种情况应记录为后续任务，而不是顺手扩张当前修改。

## 最终交付清单

- [ ] 已确认功能行为和功能测试先通过。
- [ ] 已检查本次触及区域的职责、命名、状态/副作用、依赖、重复、API、高内聚和噪声。
- [ ] 未因为行数或表面重复做机械拆分/抽象。
- [ ] 处理的既有问题与本次功能直接相关，且可独立审查。
- [ ] `refactor` commit 不含行为变化。
- [ ] 已运行最小相关 Android 验证，并在交付中列出通过项和未运行项。
