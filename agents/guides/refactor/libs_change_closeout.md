# libs 重构收尾指南

## 适用范围

用于 `libs/**` 的功能修改完成后的内部重构收尾，不替代各目录下的 `AGENTS.md`。目标不是追求更少的行数或更多抽象，而是在不改变已完成行为的前提下，让本次触及的代码更容易理解、验证和继续修改。

## 开始前

1. 阅读 `agents/rules/AGENTS.md` 和目标目录下最近的 `AGENTS.md`。
2. 按目录规则补读相关能力契约、架构说明和历史记录，先确认当前行为及其所有者。
3. 明确功能行为已经实现，并先完成针对功能的验证；收尾重构不得代替尚未完成的功能开发。
4. 使用 `git diff` 和 `git status` 确定本次改动边界，保留工作区中已有的无关修改。

## 本次重构应检查

### 1. 模块实现是否重复或漂移

如果同一能力同时存在：

- `.cpp`
- `.module.cpp`
- 共享头文件或 `.inc`

应确认两条构建路径不会各自维护同一套业务逻辑。可以抽取共享的、职责明确的内部 helper。

### 2. 公共内部接口语义是否保持

重构实现时，要确认类似 `LoadMergedToml()` 这类已有接口的职责没有被悄悄后移或改变。

即使接口不是对外公开 API，也要保持其现有语义，除非本次明确要求改变。

### 3. 派生配置是否只有一个事实来源

如果某项配置可以从另一项配置推导：

- 明确哪个是源配置
- 派生值由 loader 统一生成
- 不要让不同模块分别重新推导
- 删除已经失效的旧配置读取逻辑

### 4. 语义边界是否仍然清楚

配置映射、活动名转换、parser、validator、mapper 各自只处理自己的职责。

例如：

- alias mapping 只负责名称映射
- wake 语义由 parser / core 语义逻辑判断
- interval wake 不能因为名称匹配就被当成点事件 wake

### 5. I/O 工作流与操作顺序是否保持不变量

文件、目录、数据库或其他持久化操作应按能够保护有效状态的顺序执行。

- 先验证来源、入口文件和必要前置条件，再删除或替换目标。
- 检查步骤之间是否互相抵消，例如先复制子文件、随后删除父目录、再复制整棵目录。
- 如果一个 helper 声称安装、替换或提交完整资源，它应负责清楚的完整边界，不要让调用方猜测哪些残留内容会被保留。
- 不在普通收尾重构中改变原子性、覆盖策略、文件权限或错误恢复语义；确有必要时应作为显式行为修改处理。

### 6. 缺失、空值与非法输入是否被区分

确认 absent、empty、invalid 等状态没有被无意合并。

- 必需文件或目录缺失时，不应因为提前返回而静默表现为成功。
- 可选输入缺失时，应由拥有该契约的层明确给出默认行为。
- parser、validator 和安装/导入流程应保持各自原有的错误类型、错误阶段和错误上下文。
- 不要用无条件 fallback 掩盖构造错误、依赖缺失或损坏数据。

### 7. 同一输入是否形成一致视图

如果同一工作流需要多次读取或遍历同一份输入，检查这些步骤是否应共享同一个已收集视图。

- 目录清单、包条目或解析结果需要保持一致时，可以先收集一次，再由后续阶段验证和物化。
- 收集、协议推导、校验和物化应有清晰边界，避免一个长循环同时承担所有职责。
- 不机械追求“只读一次”；如果数据量、生命周期或实时性要求不同，多次读取可能更清楚且更正确。

### 8. helper 与中间数据结构是否仍然真实

- 删除本次工作流已经不再消费的字段、路径、包装函数和兼容分支。
- helper 名称应描述当前职责，不应继续沿用已经消失的步骤或旧格式名称。
- 中间结构应只保存后续阶段需要共享的数据；不要为可能的未来需求预留无用途字段。
- 抽取 helper 后，主流程应更容易读出阶段和不变量；如果只是增加跳转，则保留局部实现。

### 9. 格式变体是否共享规则而不混淆差异

当能力支持 manifest 存在/缺失、文件包/目录包、不同版本或不同入口时：

- 先列清各变体的行为差异和共同校验。
- 共同的路径安全、条目校验、错误映射和物化规则应只有一个事实来源。
- 入口特有的读取方式或缺省行为应留在对应适配层，不要塞入共享领域 helper。
- 不在收尾重构中顺便改变包格式、版本兼容、错误码或外部可观察行为。

### 10. 最小验证

至少运行本次能力对应的验证 profile，并确认：

- modules 构建路径通过
- 非 modules 构建路径通过
- 相关回归测试通过
- 可以获得时，结构化测试结果显示成功且失败数为零
- `git diff --check` 通过

交付时列出实际运行的 profile、测试范围、结果和未运行项。若标准入口因环境或工具链问题无法完成，可以使用仓库允许的更底层入口补充验证，但必须说明替代关系和剩余风险。

## 明确不应该做什么

- 不按文件行数机械拆分实现。
- 不为了消除一次性或上下文不同的相似代码而引入通用层、模板或配置化。
- 不把 parser、validator、mapper、存储和业务语义合并到一个“方便”的 helper。
- 不顺手统一整个 `libs/**` 的命名、格式或目录结构。
- 不在收尾重构中改变公开契约、数据格式、错误语义、覆盖策略或性能特征。
- 不把大面积格式化、行尾变化、文件移动或无关清理混进本次修改。
- 不为了追求零重复或零技术债阻塞已完成的功能交付。
- 不覆盖、回退或清理工作区中无关的用户修改。

## 发现既有问题时的范围判定

可以纳入本次收尾工作，前提是至少满足一项：

- 本次新增代码会经过、依赖或共享该区域的不变量；
- 不修会迫使本次代码复制错误模式或形成明显维护风险；
- 修复能够低风险、无行为变化地独立完成；
- 改动范围能够用一句话解释，并能用现有或聚焦测试验证。

以下情况应记录为后续任务，而不是顺手扩张当前修改：

- 只是发现文件较长、较旧或风格不统一；
- 与本次功能没有直接交互；
- 需要改变契约、格式、业务语义或大范围测试基线；
- 无法清楚审查、验证或回滚。

## 最终交付清单

- [ ] 已确认功能行为和功能测试先通过。
- [ ] 已检查构建路径、接口语义、事实来源、语义边界、I/O 顺序、输入状态、一致视图、中间结构和格式变体。
- [ ] 未因为行数、表面重复或假想复用做机械拆分或抽象。
- [ ] 处理的既有问题与本次功能直接相关，且可独立审查。
- [ ] 已运行最小相关验证，并列出通过项、替代验证、未运行项和剩余风险。
